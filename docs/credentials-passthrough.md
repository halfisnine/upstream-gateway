# New API 凭证随请求转发

日期：2026-11-17。本修订根据用户确认，移除网关上游 Key 管理和路由内部令牌；沿用完整快照、多协议渠道、多节点同步与错误隔离设计。

## 日常使用

- 网关只配置渠道标识、名称、上游根地址、启用协议、可选协议地址/认证头格式/兼容规则。
- New API 的 Base URL 指向网关 `/r/<id>`，渠道 Key 直接填写供应商的真实 Key。
- 同一网关路由允许不同 New API 渠道/请求携带各自的 Key；凭证不进入网关配置、数据库版本或普通日志。替换 Key 不需要发布网关版本。
- 管理页面登录令牌仍然有效。它与模型请求无关，不发送给上游。

## 请求规则

| 协议 | New API 发给网关的认证头 |
| --- | --- |
| OpenAI Chat / Responses | Authorization: Bearer <真实 Key> |
| Anthropic Messages | x-api-key: <真实 Key> |
| Gemini | x-goog-api-key: <真实 Key> |

网关只接受当前协议的唯一认证头。缺失、空值、重复头、多个认证载体、非 Bearer 的 Authorization、Key 中的空白/控制字符/逗号、超长 Key、被 Connection 声明为逐跳头的认证均拒绝。URL query 的 key 继续拒绝，不转发 Cookie、代理认证、转发链等其他头。

默认转发原认证头值。协议设置可以明确指定不同的上游认证头，例如 Messages 入站 x-api-key，出站改为 Bearer；只换承载格式，不换 Key。实际 New API 适配器若使用不同载体需先联调，不能自动猜测混合认证。

格式校验不是凭证有效性验证，也不是网关调用方身份认证。供应商判断 Key 是否有效；上游的 4xx/5xx 仍经固定安全错误替换，不回显原错误中的 Key。200/SSE 内嵌错误仍是现有已知缺口。

## 网络边界

移除路由内部令牌后，能访问数据端口的调用方可以选择已配置的路由。默认数据监听为回环；同机接入用受限 Docker 网络/防火墙限制 New API 来源，不发布公网数据端口。跨机器必须使用 TLS 和来源限制。该版本没有新增独立网关客户端认证头；未来需要时应与供应商 Key 分开设计。

## 配置版本与旧历史

配置 schema 从 2 升为 3，与发布序号 V1/V2/... 是两种不同概念，发布序号继续递增。

- 新增/发布的配置严格拒绝旧 key、key_set、internal_token、token_set 字段，协议独立 Key 字段同样拒绝。
- 新快照继续加密，主密钥保护配置及旧历史，不是上游 Key。
- 已保存的 schema v2 历史保持原有密文，不覆盖、不删除。因而旧密文中可能仍存在此前填写的 Key；本修订不执行破坏性的历史擦除。
- 历史读取只返回去除凭证字段后的 schema v3 配置，并标记原 schema 和“需要重新发布”。页面明确说明这是转换视图，不是旧快照原始明文。
- 恢复旧版本也先转换，再保存为新的 schema v3 快照，绝不恢复旧 Key 或内部令牌。
- 新节点拒绝把 schema v2 当成当前转发配置，报告“旧版配置需重新发布”；避免仅升级程序就悄悄改变旧路由的认证语义。加载失败按原规则保留已有有效配置，新启动且无有效配置时不就绪。

升级顺序：先确保数据网络受限 → 在 New API 将旧内部令牌替换成真实供应商 Key → 更新网关程序 → 在渠道页面核对并发布转换后的配置 → 确认所有目标节点已加载新版本。旧程序无法理解 schema v3，因此不支持新旧二进制混跑时无缝切换；本次只升级本项目本地开发实例，不修改生产 New API。
