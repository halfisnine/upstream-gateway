# 可配置错误识别与拦截规则（讨论稿）

日期：2026-11-17。状态：已按本设计开发，当前实现、默认开关和升级方式以 [实施说明](error-rules.md) 为准。本文保留讨论时的方案和建议预算；此前远程候选镜像仍只有固定非 200 隔离，新代码需单独发布候选镜像。本文不修改现行配置 schema 或已发布版本。补充需求：拦截状态可配置；提供可查询拦截日志，优先控制资源消耗。

## 目标与现状

当前 `internal/gateway/proxy.go` 在上游非 200 时直接丢弃原始正文并生成固定错误，不读取正文做分类；200 JSON/SSE 正文仍透传。没有错误规则管理页面。旧设计中的响应组件扩展方向应在此阶段具体落实，不能将设计中的扩展点当作当前已有规则引擎。

目标是让运维人员通过预设和表单配置错误规则，而不是遇到每个上游错误文案都修改 Go 代码。规则变化随完整配置版本发布和热更新；新增协议解析能力仍需更新镜像。

## 处理分层

1. **协议错误识别**：区分 HTTP 错误、200 JSON 中的结构化错误、SSE 中的错误事件。只将识别出的错误信息交给匹配器；不在模型正常回答正文中搜索“余额不足”。非标准上游可选择经验证的兼容识别器。
2. **规则匹配**：按适用渠道、协议、错误来源和字段条件匹配，支持预设与自定义规则。首版使用字段存在、字段值相等、文本包含任一关键词，以及可选忽略大小写；不引入任意脚本。渠道、协议、来源、HTTP 状态等范围条件之间为 AND；内容条件组之间为 OR，每组内字段约束为 AND，关键词列表内部为 OR。内容条件组为空时表示匹配范围内所有已识别错误。
3. **安全响应生成**：命中后按当前协议生成完整错误响应，使用管理员配置的固定公开文案和请求编号；不在原文中局部替换后继续转发，不插入原始消息、余额、Key 或账户字段。

已有非 200 隔离是强制兜底，不能通过停用规则或未命中关键词恢复原文透传。对于已经识别出的 200 JSON/SSE 错误，未命中分类规则时也使用通用安全错误。尚未识别为错误的正文不承诺被隔离；应通过真实脱敏样本补充识别能力。

## 规则与复用

完整快照增加规则定义及渠道关联（具体 schema 升级方案待实现设计）。规则具有唯一 ID、名称、启用状态、匹配条件、固定公开文案和返回状态策略；规则列表顺序即执行顺序，第一个命中后停止，不叠加改写。全局公共规则和渠道追加规则的执行顺序应明确显示，建议渠道专用规则先于公共规则，最后是强制兜底。

一个渠道仍支持多种协议；同一规则可跨协议复用，也可限定协议，不按模型品牌拆分渠道。

初始预设可包括供应商余额/额度不足、认证失效、限流、服务不可用。预设是可复制、可编辑的规则模板，采用某预设后的规则内容保存在完整配置中，后续升级镜像不得静默改写已发布版本。预设规则不会自动保证某个供应商的所有异常都能识别。

示例：

| 配置项 | 内容 |
| --- | --- |
| 名称 | 上游余额不足 |
| 范围 | 全部渠道，或选定渠道；协议可多选 |
| 来源 | HTTP 错误 / 已识别的 JSON 错误 / 已识别的 SSE 错误 |
| 匹配上游 HTTP 状态 | 可选具体状态如 402、403、429，或范围如 400–499；识别 200 内嵌错误时需包含 200 |
| 代码匹配 | 例如 `insufficient_quota`，以实际样本为准 |
| 消息关键词 | `余额不足`、`insufficient balance`、`credit balance is too low` |
| 公开文案 | `上游服务暂时不可用，请联系管理员。` |
| 对外返回 HTTP 状态 | 默认按安全策略保留原错误状态，也可指定合法的 400–599 状态；已开始的 SSE 除外 |

示例代码和关键词不要求同时满足；页面应允许建立“错误代码匹配”与“错误消息匹配”两个备选条件组，任一组满足即可。每组内各字段约束为 AND。

## HTTP 与流式语义

- 页面将“匹配上游 HTTP 状态”和“对外返回 HTTP 状态”分开，前者是触发范围，后者是处理结果。触发范围支持单值、多选和范围，区间及数量有校验上限，不支持任意表达式。选择 200 仍只匹配已识别的错误，不把普通成功响应都拦截。
- HTTP 4xx/5xx 默认保留上游状态码；其他不支持状态沿用安全 502。规则可显式指定 400–599 的错误状态，并按新状态重新生成协议错误类型；不能将拦截错误伪装成 2xx 成功。状态改写可能改变 New API 的重试/禁用策略，样本试匹配应显示原状态和拟返回状态，并纳入联调。
- 未选中的非 200 状态不命中该自定义规则，仍执行强制通用隔离；状态选择不会形成“其他错误原文放行”的旁路。
- HTTP 200 JSON 的结构化错误必须在向下游提交成功响应之前识别；转换为协议安全错误，默认使用 502，命中规则时可使用配置的错误状态。正常 JSON/usage 保持语义和字段完整。
- SSE 按完整事件解析，支持跨网络块和多行 data；不能按网络 chunk 或整段模型文本匹配。开始流式传输后不能再修改 HTTP 状态码，页面和日志必须显示“HTTP 状态已提交，返回状态改写未执行”；识别到错误时按该协议允许的错误事件格式输出安全错误并结束，不伪造成功结束、DONE 或 usage。
- 解析需限制错误正文、JSON 文档/检查窗口、单个 SSE 事件的大小和等待时长；gzip 要限制解压后大小。具体预算须在实现前给出并测试。已知错误解析失败仍兜底隔离；检查模式下超限或解析失败应有明确失败策略，不能悄悄宣称完整保护又回退原文透传。
- 全程不新增上游调用，不自动重试、续写或切换渠道。

## 运维页面与发布

新增“错误规则”页，支持从预设新增、编辑、排序、启停和删除；渠道编辑中选择公共规则及追加规则。提供样本试匹配，显示是否识别为错误、命中规则、拟返回内容；试匹配不请求真实上游，样本不写入配置历史和普通日志。

规则与渠道一起保存到草稿、发布为不可变完整版本。各节点约 5 秒检查并编译校验后切换，新请求使用新规则，已有请求继续持有旧版本。无效规则、悬空引用或不支持的组件拒绝发布/切换并报告原因，节点保留原有效配置。旧 schema 的读取、无规则默认行为和回滚兼容性需有迁移测试。

## 轻量可查询拦截日志（建议默认方案）

目标是在资源受限生产节点上支持排查，不构建全量模型请求日志平台。采用现有 PostgreSQL 的独立日志表，不引入 Redis、Elasticsearch 或新的日志服务；日志不写进不可变配置快照，也不随版本回滚。

### 内容及查询

- 只记录规则拦截和强制兜底的上游错误，一次请求至多一条拦截事件；不为每个 SSE 分块或每次规则尝试写日志。
- 有界字段包括事件 ID、时间、请求编号、节点/实例、渠道 ID、协议、配置版本、规则 ID、匹配条件组编号、固定原因分类、上游 HTTP 状态、拟返回状态、实际已提交状态、SSE 错误事件/终止方式。规则删除后仍能按历史配置版本找到当时定义。
- 不保存完整请求/响应、聊天内容、认证头、Key、供应商账户信息或原始错误正文，也不保存匹配到的原始片段。页面通过规则 ID、分类和状态解释命中原因；原文样本试匹配与持久日志分离。
- 管理页新增“拦截日志”，按时间、渠道、规则、状态、节点或请求编号查询，默认近 24 小时，每页 50 条、最多 100 条，使用游标翻页；不默认做全表 COUNT 或全文搜索。只建时间/游标和请求编号等必要索引，其他组合先在受限时间范围中过滤，再据实测增加索引。
- 日志 API 复用管理员认证。页面明确区分上游 HTTP 状态、实际返回状态和 SSE 内嵌错误，不能把 HTTP 200 的流内失败当作成功。

### 请求路径与预算

请求处理只生成小型元数据记录，使用非阻塞入队；单个后台写入器批量写数据库。不得在请求处理中同步 INSERT、等待队列空位、启动逐请求 goroutine、落盘正文或因日志故障改变模型响应。

建议起始预算（不是已测性能承诺）：

| 项目 | 建议默认值 |
| --- | --- |
| 每节点队列 | 最多 1024 条，单条编码后最多 1 KiB，各字段在入队前限长 |
| 后台刷新 | 每秒最多一个批次，每批最多 50 条；正常低负载约 1 秒后可查，积压时更久 |
| 写入连接 | 每节点独立最多 1 个数据库连接，不挤占现有配置读取/发布连接池 |
| 写入超时 | 每批 1 秒；失败指数退避，上限 30 秒，不忙循环 |
| 重试 | 批次重试也计入上述有界预算；使用稳定事件 ID 去重，不能无限堆积 |
| 默认保留 | 最长 3 天，并以全局最近 5 万条为清理目标，任一条件达到就清理旧记录 |
| 清理 | 单个节点获得数据库维护锁后每分钟小批量删除，避免所有节点重复清理或长事务 |

1024×1 KiB 约为 1 MiB 编码载荷预算，不等于 Go 实际 RSS；批次、对象、索引、数据库缓存、WAL 和空闲页仍有开销，必须实测。3 天/5 万条是定时清理目标，会有短暂超出，不是数据库文件大小硬上限；监控表/索引/WAL体积及 autovacuum，正常情况下复用空间，不频繁 VACUUM FULL。每节点写入上限乘以节点数量才是集群写入预算。

### 资源保护与日志完整性

- 正常容量下，每次拦截都尝试记录，默认不抽样。队列满时丢弃新增详细记录，业务拦截仍正常执行；持续数据库故障下，不能无限使用内存或占满磁盘。
- 节点心跳报告待写数量、累计丢弃数、写入失败数、最后成功写入时间；数据库恢复后页面能看到记录不完整的告警。累计指标按进程实例区分，突然崩溃前未上报的计数不能保证恢复。
- 日志查询失败必须报数据库不可用，不能显示为“没有拦截”。页面显示写入延迟和降级情况，不把“查询不到”解释成“请求未被拦截”。
- 正常停止在固定超时内尽力排空；强制结束或崩溃可能丢失尚未写入的记录。此方案承诺有界资源与正常情况下可查，不承诺极端故障下逐条零丢失。若后续要求审计级零丢失，需要另行选择持久化队列及磁盘/延迟预算，不能同时承诺零阻塞、有限资源和任意故障零丢失。

设计时的代码在每个模型请求结束时会同步调用 `slog.Info` 输出到标准错误。实现此方案时一并调整：常规成功请求默认不逐条打印，保留必要的聚合运行信息；拦截明细进入上述异步管道，避免再重复输出一份。后台写入失败的运行日志限频，并为 Docker 日志设置轮转和大小上限，避免把压力从数据库转移到 stdout 或容器磁盘。

规则文本及返回状态随业务配置版本发布；日志队列、写入限额和保留策略属于运维资源设置，应有硬上限，不能通过恢复旧规则版本悄悄扩大或清空日志。配置读取与日志表故障隔离需在实际 PostgreSQL 上验证。

## 必须通过的验收

- 非 200 命中、未命中、无自定义规则、坏 JSON、超限、压缩错误均不泄露原错误。
- 各协议 200 JSON 和 SSE 的明确错误样本被识别与替换；未知格式清楚标注支持边界。
- 正常模型回答中讨论“余额不足”、JSON 示例或 error 字样时不误拦截；正常 usage、结束语义保留。
- SSE 分块、多行事件、错误发生在首事件/流中途、取消与超限；不伪造完成，不增加调用。
- 公共与渠道规则顺序、启停、版本恢复、双节点同步及旧流跨规则更新。
- 页面样本测试不触发真实请求；错误文案和样本不能形成 XSS 或泄露到日志。
- 状态多选/范围校验、状态和文本组合、只有状态条件、配置返回状态、已开始 SSE 无法改 HTTP 状态；New API 错误类型与重试/禁用兼容。
- 有界日志队列、批量写入、数据库失败退避、队列满降级、事件去重、正常排空与重启、全局保留清理；日志故障不得阻塞转发或配置同步。
- 管理员日志查询、游标翻页、删除规则后的历史解释、日志不完整提示；日志和普通运行输出不包含真实凭证或原始正文。
- 比较关闭/开启日志时正常流量和持续全部错误场景的延迟、CPU、RSS、数据库写入、WAL/磁盘增长；在目标生产资源限额下验收。

实现应先完成独立解析/匹配/输出组件和模拟上游回归，再接入版本化配置及页面，并通过真实 New API 联调后确认覆盖范围。
