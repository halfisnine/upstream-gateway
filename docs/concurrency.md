# 动态并发上限

本功能属于开发候选，生产容量未经过压测。可设置的上限不代表机器能够承载该并发。

在「渠道配置 → 并发设置」展开表单，编辑后点击「发布完整配置」。并发设置与渠道、错误规则一起保存为不可变全量版本，各节点约每 5 秒同步，使用节点页面的已应用版本确认生效，不需要重启。

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `traffic_limits.node_concurrency` | 32 | 每节点同时处理的模型请求总数 |
| `traffic_limits.upstream_concurrency` | 16 | 每节点到同一上游的同时请求数 |

两个值都是整数，范围 1–8192，上游上限不能大于节点上限。JSON 中省略字段或使用 0 表示默认值，不表示无限；表单要求填写明确的正整数。非法配置拒绝发布/应用，继续使用旧配置。历史比较、恢复及导出包含这些设置。

上游按 scheme、主机名（不区分大小写）和端口归组，省略默认端口与显式 80/443 归为同组。不同渠道、路径、Key、模型或 API 协议指向同一目标时共享额度；不同域名即便解析到同一 IP 也不合并。HTTP/1.1 请求和 HTTP/2 流各占一个名额。限制只管本节点，不是数据库锁或集群配额。多个节点的总上限会叠加，需自行配合上游账户的共享配额。

请求通过路由、认证及基本请求校验后，原子检查节点与上游两个额度；超限立即返回对应 API 协议的安全 503 和 `Retry-After: 1`，不发起上游请求、不排队、不自动重试。不记作上游错误拦截日志。请求从获准到响应结束（包含上传、连接、等待响应和 SSE）持续占用额度；结束、取消、连接失败等路径释放额度。节点页面现有「在途请求」包含这些已获准请求。

发布调高上限后，新请求可以立即使用新名额；调低时已有请求继续，不取消旧 SSE。当现有计数下降到新上限以下才重新接收。计数不按配置版本清零，避免频繁发布绕过上限。新请求使用最新已应用的额度，已开始请求持有的路由及错误规则仍使用原快照。共享 Transport 保持不变，因此更新并发不会重建连接池或打断连接。

旧实现的节点总限制为 32，同一上游 Transport 连接限制为 16；节点满返回 503，上游连接满会等待。新实现默认仍为 32 / 16，但上游限制改为请求准入，超限立即 503，HTTP/2 也适用。Transport 不再设置固定 16 的连接瓶颈，空闲池仍受 128 总连接 / 每主机 8 条的限制。入站 TCP 连接数量、无效/慢请求及恶意流量不由业务并发上限覆盖，入口网络与 HTTP 服务超时仍是独立保护。

## 升级顺序

配置 schema 为 5；新程序可以读取 schema 3/4，默认使用 32 / 16，schema 4 的错误规则和检查开关保留。无需新增数据库迁移。先更新所有节点到支持 schema 5 的镜像，再发布新配置；旧镜像不能读取 schema 5。恢复旧历史会转换并发布为新的 schema 5 版本，采用默认并发上限，不覆盖历史记录。程序降级需另行处理配置兼容性。

## 容量规划

注册/在线用户数不等于同时生成数。例如 4000 个在线用户，10% 同时生成约为 400 并发；4000 人全部同时生成则是 4000 并发。稳定负载下可以用每秒新请求数 × 平均请求时长估算在途量，突发和长尾需额外余量。

当前 Docker 验证节点是 1 CPU / 256 MiB，保持默认值，不能直接把 4000 填进去当作容量保证。200 JSON 检查会完整读取最多 8 MiB 正文，缓冲及解析内存随并发叠加；SSE 按事件读取，单事件最多 256 KiB，但连接、TLS、解析、慢客户端仍占用资源。异步错误日志每秒最多一批 50 条，持续错误风暴可能丢弃明细。

本次功能测试验证 HTTP/1.1 和 HTTP/2 各 40 条活动流跨过旧限制、动态调低不中断旧流、超限不访问上游、跨版本计数共享、结束后释放以及并发竞争。该测试用于验证行为，不是 1 CPU / 256 MiB 的容量压测。未来需要在目标容器资源限制下用模拟上游测正常 SSE、长响应、开启检查和错误风暴，记录 RSS、CPU、首包延迟和拒绝率，再决定单节点配置及节点数。扩展节点还需在 New API 与网关之间安排流量分配；配置同步本身不负责负载均衡。
