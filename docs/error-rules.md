# 可配置错误处理与拦截日志

2026-11-17，配置 schema 4。开发验收结果见 [验收记录](error-rules-validation.md)。实现覆盖规则管理、版本发布、标准协议错误检查和异步元数据日志；未知供应商响应、真实 New API 重试/禁用行为和目标生产容量仍需独立验收。

## 使用流程

1. 先配置渠道。在「错误规则」页从预设新增，或建立自定义规则。
2. 选择渠道（公共或指定渠道）、协议（可多选）、错误来源与上游 HTTP 状态范围。内容条件组之间为 OR，组内条件为 AND；每个条件的值列表为 OR。支持错误 code/type/message 的存在、相等、包含匹配及忽略英文大小写。不支持脚本或任意正则。
3. 配置返回 HTTP 状态与固定公开文案。返回状态留空/0 表示保留原 4xx/5xx，其他情况用 502；指定值必须是 400–599。请求编号由网关追加，不把上游原文插入文案。
4. 使用「样本试匹配」验证当前表单替换草稿后的完整规则链。它仅处理手工填写的已提取字段，不解析原始报文、不发起上游请求、不保存样本，不能代替真实协议联调。
5. 需要检查 HTTP 200 错误时，勾选「检查 HTTP 200 JSON / SSE 内嵌错误」。默认为关闭，以保持现有转发兼容性。保存规则到草稿，发布完整配置，再检查所有目标节点版本。
6. 在「拦截日志」查询请求编号、规则 ID、渠道、实际状态、节点和时间。日志一般约 1 秒后可见，有积压或退避时更久；节点心跳约 5 秒更新。

指定渠道规则优先于公共规则，各组内按列表顺序执行，首条命中即停止。排序、启停、修改和删除都需要发布。被规则引用的渠道必须先移除关联才能删除，避免专用规则意外变成全局规则。一次请求持有完整旧快照，更新配置不会改变已开始的 SSE 使用的规则。

## 支持范围和预算

- **非 200**：始终隔离原始正文。读取最多 64 KiB 解压后的错误正文，最长 2 秒；从结构化错误或错误消息中匹配规则。读取失败、超限或异常压缩时执行通用安全兜底，不进行不完整文本匹配。
- **200 JSON（开启检查时）**：最多 8 MiB 解压后正文，完整读取最长 30 秒。识别顶层 `error`、明确 `type: error`，以及 Responses `response.failed` / `status: failed` 的失败封套。解析失败、重复封套键或超限时返回安全 502，不转发无法检查的正文。普通模型输出中的 `error` 字样、JSON 示例或“余额不足”不会被扫描。
- **SSE（开启检查时）**：以完整事件为单位，支持跨网络分块、多行 data、LF/CRLF/CR 换行和初始 BOM；每事件最多 256 KiB，读取最长 30 秒。识别协议错误对象、`event: error`、Responses 失败事件。正常事件的字节顺序、usage 和结束标记保留。解析失败、超限或不完整事件停止原文转发，生成安全错误。
- 在首个 SSE 事件提交前发生错误，可返回配置的 HTTP 错误状态。流已开始后保留已提交状态（一般 200），发送对应协议错误事件并结束；不追加伪造的 DONE、成功完成或 usage。日志分别记录拟返回和实际状态。OpenAI Responses 使用 `event: error` 与顶层 `type/code/message/param`；Messages 使用 `event: error` 和协议错误封套；Chat/Gemini 使用 data 错误封套。
- gzip 检查使用解压后字节预算；开启检查后正常响应可能改为未压缩转发，正常 JSON 内容及正常 SSE 拼接字节保持不变。关闭检查时沿用原始 JSON/SSE/gzip 转发。
- HTTP 状态改写会影响 New API 的错误判定；网关自身不重试、不续写、不切换渠道。
- 非标准上游错误如藏在普通消息内容中，不属于已知错误结构；Sub2API / kiro2cc 必须用实际版本的脱敏样本验证，不宣称全部覆盖。

规则上限 128 条；每条最多 8 个条件组，每组 8 个条件，每条件最多 16 个值；单值最多 256 字节，公开文案最多 1,024 字节，状态范围最多 16 段。非法配置拒绝发布，节点继续使用原有效快照。

## 日志资源与完整性

使用现有 PostgreSQL 独立表 `gateway_interceptions`，不增加其他服务。每个上游错误拦截至多一条记录，包含时间、请求编号、节点/进程实例、渠道、协议、配置版本、规则 ID、条件组、固定原因分类、上游/拟返回/实际状态和处理方式。另外保留被拦截正文的受限原始片段，用于管理员核对误拦；不记录完整请求或成功会话。正常成功请求不再逐条输出 `slog.Info`；日志写入失败通过计数和心跳报告，不重复逐条打印。

每节点队列最多 1,024 条且编码载荷总计最多 1 MiB，包含正在重试的批次；单条含密文的记录编码后最多 4 KiB，较大的记录会让可排队条数相应减少。请求线程仅生成元数据、加密受限片段和非阻塞入队，不同步 INSERT，不为每请求启动 goroutine。单个后台写入器每秒最多一批，每批最多 50 条，写超时 1 秒；失败指数退避至 30 秒。日志数据库连接池最多 1 个连接，与配置池分离。稳定事件 ID 去重。容量内不抽样；队列满、关闭后入队或记录超限时丢弃明细并累计计数。

保留目标为最近 3 天且最多最近 50,000 条。数据库维护锁和一分钟租约只允许一个节点清理，每轮最多删除 10,000 条。它是软目标，并非数据库文件硬上限；极大集群持续写入可能超过清理能力，需监控表、索引、WAL 和 autovacuum。不会频繁 VACUUM FULL，也不会因恢复配置版本删除日志。

日志页面默认近 24 小时、每页 50 条，API 最多 100 条/页、时间窗口最多 72 小时，使用时间与 ID 游标翻页，不做全表 COUNT。日志 API 同样需要管理员认证和同源校验。查询失败明确报错，不假装没有记录。

心跳包含待写、累计丢弃、写入失败、最近成功/失败时间及进程实例。正常停止最多用 2 秒排空；进程崩溃、数据库长时间不可用会丢失明细，尚未上报的计数也可能丢失。日志中的状态表示网关选择并尝试输出的响应，不证明客户端已完整接收。该功能用于运维排障，不是零丢失审计日志。

验证 Compose 为网关、迁移和 PostgreSQL 设置 Docker 日志轮转：每文件 10 MiB、最多 3 个文件。日志资源预算目前是有上限的代码默认值，页面只读展示，不提供未经约束的任意调整。


### 查看原始错误以排查误拦

打开「拦截日志 → 详情 → 上游原始错误」，点击「查看原始错误」后才加载并解密。列表不携带明文或密文，详情 API 复用管理员认证、同源检查和 `Cache-Control: no-store`。页面以纯文本展示，HTML / script 不会执行。

- HTTP / JSON 保存被拦截的解压后响应片段；SSE 仅保存当前出错事件，不收集之前的正常回答。解析失败、超限或读取中断时，尽可能保留已读到的前缀，因此也能定位格式误判。
- 每条最多 2 KiB UTF-8 文本；超过长度或上游未读完整时明确标注“已截断或读取不完整”。未知编码等无法取得正文时显示“原文不可用”，不能伪装成空正文。旧日志显示“未采集”，无法补回。
- 加密前移除当前请求 Key 的常见明文、JSON 和 URL 编码形式，以及常见 JSON 凭证字段与 Bearer token；页面显示是否发生脱敏。保留其他错误字段用于排障。自动脱敏不是对所有未知供应商私有字段的保证，原始片段可能包含上游账户信息或误拦的响应内容，仅管理员可见。
- 使用现有主密钥派生独立 AES-256-GCM 日志密钥，每条随机 nonce，并绑定事件 ID。数据库不保存原始片段明文；加密失败仍记录元数据，绝不退化为明文存储。所有节点需要相同主密钥才能查看原文。
- 原文与事件同一行保存、同一保留周期删除，不增加额外写入事务。上线先执行新镜像 `--migrate` 扩大事件行约束。无需改变业务配置 schema 或重新生成密钥。

2 KiB 原文经加密和 base64 后会增加磁盘与 WAL 占用；最近 5 万条满长原文约 98 MiB 明文载荷，密文、JSON、行、索引及 WAL 另计。队列新增字节预算限制积压载荷，不能将其解释为进程总内存仅 1 MiB。

## 升级、回滚和发布

先执行新镜像的 `--migrate`，再启动新节点。迁移仅增加日志表、索引、维护租约表及 `gateway_nodes.log_stats` 列，保留原有不可变配置历史。新节点可以读取 schema 3 快照，保持正文检查关闭、无自定义规则；schema 2 仍需先在 New API 改为真实凭证并显式重新发布。

新发布与恢复历史均生成 schema 4 完整快照。旧 schema 3 二进制无法加载 schema 4；先升级所有节点再发布新配置，不能依赖新旧二进制混跑自动兼容。回滚规则优先用当前镜像恢复旧配置为新版本；恢复 schema 3 历史会关闭正文检查。程序降级需要单独确认快照和数据库兼容性。

本地开发、镜像发布和生产部署是独立动作。静态原型保留在 `prototypes/error-rules/`，不会进入正式控制台或镜像。

## 可复现验证

```sh
CGO_ENABLED=1 .dev/run go test -race ./...
.dev/run go vet ./...
# 创建并清理专用 PostgreSQL 与两个本地节点；需要已安装的项目 Playwright 缓存。
python3 scripts/check-error-rules.py
# 不修改真实配置的原有控制台布局回归。
FONTCONFIG_FILE="$PWD/.cache/fonts.conf" \
PLAYWRIGHT_MODULE="$PWD/.cache/browser/node_modules/playwright" \
PLAYWRIGHT_BROWSERS_PATH="$PWD/.cache/browser-binaries" \
node scripts/browser-layout-smoke.cjs
```

普通单元测试不会连接数据库；PostgreSQL 测试需运行 `scripts/test-database.sh <测试阶段镜像>`。其用一次性数据库验证事件去重、同时间游标分页、保留清理，以及日志表不可用时转发和配置同步仍正常。浏览器验收创建空数据库，非空数据库会拒绝继续。

性能检查必须区分匹配/排队微基准和真实 PostgreSQL、CPU、RSS、磁盘表现。固定队列只是资源上限，不能据此承诺总 RSS 仅 1 MiB 或生产性能无损；32 个并发大 JSON 检查仍有显著缓冲与解析开销。生产容量、错误风暴下的记录完整性与 New API 计费联调必须在目标资源限额下验证。
